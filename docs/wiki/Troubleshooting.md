# Troubleshooting

| Symptom | Likely cause | What to do |
|---|---|---|
| `./demo.sh model` stops with `ZRT's service for the model keeps restarting`, or the unit stays `activating` while `zrt services` shows the model `Pending` with a short uptime | vLLM crashes and ZRT restarts it; on a test machine the serve script's `/usr/local/cuda-13.3` did not exist (#533) | Read the diagnosis it prints. CUDA: `ls -d /usr/local/cuda*`, then `echo AWARECARE_CUDA_HOME=/usr/local/cuda-13.0 >> ~/.config/aware-care-demo/model.env` (a directory with `bin/nvcc`) and `systemctl --user restart aware-care-zrt-model.service`. Also `zrt logs tail <label> --lines 50` and `nvidia-smi --query-compute-apps=pid,process_name,used_memory --format=csv` |
| `./demo.sh` prints `ZRT's proxy on 8080 does not list the model; using the service endpoint http://127.0.0.1:<port>/v1`, or stops with `ZRT does not serve <model> ... on http://127.0.0.1:8080/v1` while `zrt services` shows it `Ready` on another `API ENDPOINT` | ZRT runs the model as a service with its own endpoint, and its proxy on 8080 does not route to it (on an HP Z8 the proxy listed another model, #535) | Nothing, if it found the endpoint: the app and the deploy tool use it. Otherwise pass it: `./demo.sh setup --zrt-port <port>` (or `--zrt-url http://127.0.0.1:<port>/v1`, or `AWARECARE_ZRT_URL`; loopback only). A proxy on another port than 8080 needs nothing: `demo.sh` reads `zrt config get proxy.port` (#549). When `./demo.sh` prints `Nothing on port <n> lists the model; port <m> serves it`, another listening loopback port serves it (for example another account's ZRT, #632): nothing to do, or pass `--zrt-port <m>`; do not serve it again with `./demo.sh model`. A service's endpoint can change when it restarts, so for a lasting setup serve the model through the proxy (`./demo.sh model`) |
| `docker buildx is missing` | None of the forms works: the Docker buildx plugin (`docker buildx version`), the standalone `docker-buildx` program, the plugin binary in a `cli-plugins` directory run directly, or `docker docker-buildx` answering as buildx (it usually prints Docker's own version, which proves nothing) | Install the plugin or the standalone program; `demo.sh` and `build_images.sh` use whichever works (#535, #549) |
| `! Docker CLI: .../miniconda3/bin/docker, from the conda environment base, comes before /usr/bin/docker` (on an HP Z8, `docker buildx version` failed in a conda "(base)" shell) | The conda environment brings its own Docker CLI, which does not find the system's CLI plugins | `conda deactivate`, then rerun; or `PATH=/usr/bin:$PATH ./demo.sh setup`. `demo.sh` still finds buildx as the plugin binary (#549) |
| `ZRT's proxy is set to port <n> (zrt config get proxy.port), so ZRT would serve <model> there` | `--zrt-port`, `--zrt-url` or `AWARECARE_ZRT_URL` names another port than ZRT's proxy uses; a model served by ZRT is reached through that proxy | Leave the option out (`demo.sh` reads ZRT's port), or set ZRT's: `zrt -m <mode> config set proxy.port <n>` (in system mode for every user of ZRT: an administrator decides) (#549) |
| `./demo.sh` prints `! Serving revision main; this app was qualified on 95a723d…` | ZRT serves the right model, but another revision than the one the app was qualified on | Nothing: it works. To serve the qualified revision, stop the other one (`zrt stop hf:<repo>@main`), then `./demo.sh model --revision <qualified commit>` (the `MODEL=` line of `infra/<device>/zrt/serve-model.sh`) |
| The model came back by itself, or `./demo.sh status` says `Watchdog: on, but it gave up after 3 restarts within an hour` | The watchdog (#640) restarts `aware-care-zrt-model.service` when the unit is meant to run but ZRT lists no model and no ZRT service process for it lives (a vLLM crash, a ZRT reinstall or update, a GPU error); after 3 restarts within an hour it stops trying | `journalctl --user -u aware-care-zrt-watchdog.service` (its decisions) and `journalctl --user -u aware-care-zrt-model.service`; fix the cause (see the `./demo.sh model` rows), then `./demo.sh model`, which also resets the count. To keep the model off, stop the unit (`systemctl --user stop aware-care-zrt-model.service`): the watchdog never starts a stopped unit |
| Telemetry shows the energy and the device's cost as `Not measured` ("Power sampler not running"), or `./demo.sh setup` prints `! Power sampler off: its crontab line could not be added` | The GPU power sampler (`infra/telemetry/power_sampler.py`) runs from one user crontab line per data root, which `setup`, `local` and every local-mode deploy add themselves (#678). Either the crontab could not be written (no cron, or `crontab` refused for your user), or the app was deployed in mock mode, or the sampler cannot read the GPU (`<data root>/telemetry/sampler.log` says why) | `./demo.sh status` shows `Power sampler: on`, its crontab line and its last reading. Once `crontab -l` works for you (an administrator installs `cron`), rerun `./demo.sh setup`. Within a minute Telemetry says "Power sampler active"; the energy counts from then on. Until then, and on a new installation until the first full metered hour has passed, each Not measured figure says when it will appear (#693) |
| `ZRT does not serve <model>` although ZRT runs it | ZRT serves no copy yet (still starting, up to 6 minutes on a Nano), or it stopped after a reboot or logout | `systemctl --user status aware-care-zrt-model.service`; to keep it running after logout, the account that serves the model needs lingering: an administrator runs `sudo loginctl enable-linger <user>`. The same model under ZRT's own name or another revision counts as served |
| `./demo.sh status` says the deployment runs another commit than the checkout | The checkout changed after the last deploy | `./demo.sh update`, or `./demo.sh local` to deploy the checkout as it is |
| `./demo.sh setup` or `local` says `It's already running: open it here`, then `The release <tag> from the deploy workflow` (or `The ./demo.sh instance of <account>`, `Your own instance with its data in <dir>`, or `A demo answers on 127.0.0.1:8180` when Docker is not usable for you) | The machine already runs a demo under the same container names. There is no main instance (#644, #696) | Open it with the tunnel and address it prints; `./demo.sh open` prints them again at any time (#695). To run yours instead: `./demo.sh setup --replace` (its containers are removed, its data is kept; on the maintainer's devices the next deploy brings the release back). To run yours beside it: `./demo.sh setup --instance my-demo --api-port 28100 --web-port 28180`. If it does not answer at all, wait 2 minutes; if it answers `degraded`, its model is not served: `./demo.sh status` shows what ZRT serves, and the account that serves the model starts it again with `./demo.sh model` (#654). `./demo.sh status` names whose demo runs and where its data stays (#652) |
| `./demo.sh setup`, `model`, `local` or `doctor` says `An administrator must do <n> things for <user>, once` | The account is not in the `docker` group, not in the `zrt` group while its ZRT runs in user mode and the system ZRT holds the model (or its cache cannot be read), or has lingering off while it serves the model (#694) | Pass the block it prints to an administrator, unchanged: it names the account (`sudo usermod -aG docker,zrt <user>`, `sudo loginctl enable-linger <user>`). Then log out, log in again over SSH as that account, and rerun the command it names |
| `./demo.sh model` or `setup` stops with `The GPU has <n> GB free, and <model> asks for about <m> GB` | Another model or program fills the GPU (on the shared Fury another account's model used 151.6 of 256.7 GB, #702) | Your own other model: the `Run:` line stops it (`zrt -m <mode> service stop <uri>`). Someone else's: ask them; `nvidia-smi` and the message name the processes and their owners |
| `status` or `doctor` says `ZRT serves the model, but it was started outside demo.sh` | The model was started by hand (`zrt service start`), so no unit and no watchdog bring it back after a crash or a reboot (#702) | `./demo.sh setup` adds the unit and its watchdog; the model keeps running |
| `./demo.sh update` says `Already on the newest release origin has` or `This checkout is at or past <tag>`, and nothing changes | origin has no newer `v*` release tag than this checkout (#702): a fork or a copy has only the releases published to it. Any origin is accepted; without a tag named, update never moves to an older release | Check where origin points (`git remote -v`) and which releases it has (`git ls-remote --tags origin`); name one with `./demo.sh update <tag>` |
| `./demo.sh setup`, `model` or `local` stops with `systemctl --user cannot reach your systemd session (Failed to connect to bus: Permission denied)` | You switched user with `sudo` then `su <user>`, which starts no systemd user session; the model unit is a user unit (#644) | Log in over SSH as that user (`ssh <user>@localhost` works on the machine itself), then rerun |
| `The system ZRT already has this model: ... so demo.sh does not download it again` | ZRT runs in user mode (its own cache in your home), but the system ZRT's cache `/opt/hp/zrt/models` holds the model; a download would take an hour and the disk twice (#644) | In the `zrt` group: rerun with `--zrt-mode system`. Otherwise an administrator runs `sudo usermod -aG zrt <user>`; log in again, then rerun with `--zrt-mode system` |
| `ZRT's service for <model> looks stuck: its log ... has not changed for 10m00s`, or `ZRT did not serve <model> within 60m00s` | Past the usual wait (15 min Nano, 8 min Fury) `demo.sh` waits on while ZRT's process for the model lives and its log changes (a first start in a fresh ZRT builds GPU kernels for about 25 min, #644); it stopped because the log stood still for 10 min, or after 60 min in all | `zrt logs tail <label> --lines 50` and `journalctl --user -u aware-care-zrt-model.service` show where it stopped; fix that, then `./demo.sh model` |
| `./demo.sh local` stops with `Port <n> is in use on this device (local uses API 8100, web 8180)` (or, from the deploy tool, `loopback port(s) [...] are in use by another process`) | Another program holds the device port 8100 or 8180 | `ss -ltnp \| grep -E ':(8100\|8180)'`; stop it, or run a second instance on other ports as in the row above |
| Every answer says it is scripted, or the badge says "Mock mode" | The app runs in mock mode | `./demo.sh local` for the device's model |
| `docker pull` of `ghcr.io/your-github-user/...` is denied or asks for a login | The released images are private | `./demo.sh local` builds the images itself; no login needed |
| `./demo.sh` shows escape codes such as `\033[32m` instead of colors | The terminal does not understand ANSI colors, or `FORCE_COLOR` is set | `./demo.sh <command> --no-color`, or `unset FORCE_COLOR` (it wins over `NO_COLOR`; without it, `export NO_COLOR=1` also works) |
| A consultation shows Try again after the API restarted | The restart interrupted its guidance job (#263) | Retry from the guidance page; the answers are kept |

| Setting up another device: "Accept and begin" (or Start presenter session) says "Open Aware Care at the address this device is set up for" (the API refused the origin, `403 ORIGIN_REJECTED`) | The browser opened the site at an address the deployment does not accept: another tunnel port or a host name (`localhost` is redirected to `127.0.0.1` on the same port since #690).
