# ADR-009: Milestone 2 records, profile context and patient-screen decisions (mock mode)

Status: engineering decisions for the development build, pending product/clinical/technical review.
Date: 2026-10-13. Change record: CHG-DEV-APP-003 (`../change-records-archive.md`). Supersedes ADR-007 #4; extends ADR-008.
Affected IDs: R03, R04, R09, R10, R13, R15, R18, R19, R20, R27, R33, R35, R36; A02, A04, A06, A08, A13, A14, A16;
M02, M03, M04, M06, M11; uploadRecord, listRecords, reviewFact, createCase, editCase, saveAnswer, deleteSession.

No requirement, route, operation ID or schema changes. Each item should be confirmed or replaced by the named owner.

| # | Topic | Decision in this build | Reason / open dependency |
|---|---|---|---|
| 1 | Record extraction in mock mode | `uploadRecord` runs the full R18 validation, stores accepted bytes under an opaque key in `data_dir/records` (0600) and queues a `record_extraction` job. In mock mode the job extracts only from the bundled **synthetic sample record** (`fixtures/records/`), recognized by the SHA-256 of its exact bytes. The scripted fact comes from `profiles.json` `record_samples`. Any other valid file ends `failed` with `EXTRACTION_UNAVAILABLE`, and its bytes are deleted. Local mode returns 503 `SERVICE_LIMITED` before storing anything. | Mockup A04: "No real file upload. A bundled fictional document is used." The bytes-keyed trigger never invents facts about a user's file. A real parser/OCR worker remains an ADR-002/ADR-004 dependency. Supersedes ADR-007 #4 (blanket 503). |
| 2 | Sample record files | `scripts/make_sample_records.py` regenerates `synthetic-sample-record-01.pdf` and a truncated `synthetic-unreadable-record.pdf` deterministically with the export PDF writer. `manifest.json` declares `data_mode: synthetic`. The loader keys samples by the actual bytes on disk, not the manifest hash. A04 uploads these same files (Vite `server.fs.allow`), so there is a single copy. | Fixture README: no real PDF or OCR result is claimed; the sample is labeled fictional. |
| 3 | Validation order and codes | Declared type ∉ {pdf, png, jpeg} → 415 `RECORD_TYPE_UNSUPPORTED`. Signature ≠ declared type → 415 `RECORD_TYPE_MISMATCH`. Size > 10 MiB → 413 `RECORD_TOO_LARGE` (the route reads at most limit+1 bytes). Empty or truncated (no `%%EOF`/`startxref`, no page) → 422 `RECORD_MALFORMED`. `/Encrypt` → 422 `RECORD_ENCRYPTED`. JavaScript/JS/Launch/EmbeddedFile/RichMedia/OpenAction → 422 `RECORD_ACTIVE_CONTENT`. Image > 40 MP → 413. Validation runs before any write. | 03-data-and-api "Record processing"; R18. |
| 4 | Per-case limits | Every accepted upload, including failed ones, counts toward the 3-file limit (413 `RECORD_LIMIT`); an upload answered 503 because its extraction could not be submitted was never accepted and does not count (#628). Only held records count toward the 30-page budget (413 `RECORD_PAGE_LIMIT`). The check and the reservation happen in one serialized transaction. | `RecordList.documents` has `maxItems: 3`, so failed documents must also count. |
| 5 | Stale and deleted extraction | The worker publishes only if the case still exists, is not deleting, and is at the upload revision. Otherwise the job is `cancelled`/`stale`, the document `failed` (`REVISION_CHANGED`), and the bytes are deleted. | R27 and 05-privacy "late output cannot recreate deleted content". |
| 6 | Fact review | `confirm` → `confirmed`. `reject` → `rejected`. `correct` → `confirmed` with the corrected value/units, while `original_text` and the stored bytes are never rewritten. Each action writes a `fact_reviews` row with prior and new values. The revision bumps (with invalidation) only when the confirmed set or a confirmed value changes; rejecting an unconfirmed fact changes nothing. `next_action` is `records` before any question is issued, `intake` afterwards. | The Fact status enum has no `corrected` value; R20 "without changing the original source". |
| 7 | Unconfirmed facts | `cases.repository.facts()` returns confirmed facts only, so case `confirmed_context`, guidance and exports never see unconfirmed or rejected extractions. A04 lists them with `document_facts()`. | R20. Before this change every fact was confirmed, so behaviour for existing data is unchanged. |
| 8 | Profile context semantics | `createCase`/`editCase` validate known kinds server-side. `null` means explicit unknown. A missing `allergy_status` is stored as `unknown` (never "none"). `allergies` is required exactly when the status is `reported`. Age is a whole number from 18 to 130 (matching A02). History/medications must be non-empty text or null. Duplicate kinds are rejected. | R04. Clinical rules belong on the server, not only in A02. |
| 9 | Context edit scope (defect) | Editing `confirmed_context` replaces profile-context facts only. Answer mirrors and fixture signals stay active. | Previously a context edit deactivated every user-provenance fact, silently erasing intake answers. |
| 10 | Strict answer scalars (defect) | `AnswerWrite.value` uses `StrictStr`/`StrictInt`. JSON booleans and floats are rejected (422) instead of being coerced to `1`. | The contract has no boolean; R13. |
| 11 | Upload response | 202 returns `UploadRecordResponse` `{document, job_id}`. | OpenAPI contract; an earlier draft returned `Job`. |
| 12 | Whole-page empty states | `EmptyState page` renders its title as the page `h1` (not found, step complete, no guidance, out of date, review required). In-page empty states keep `h2`. | The width sweep found pages with no h1 (accessibility). |
| 13 | A14 end session | Uses the shared `useEndSession`. Browser state is cleared only after the server accepts `deleteSession`; a failure is shown in the dialog with retry. "Delete selected data" was relabeled "Delete all consultations" to match its action. | Previously a failed request still cleared state and navigated away: a false deletion signal. |
| 14 | Saved accounts | Unchanged: no saved profile/resume (ADR-005). R05 and the saved-account part of R10 remain untestable. | ADR-005 open. |
