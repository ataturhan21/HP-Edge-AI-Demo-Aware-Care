# ADR-011: Wiki before issue closure

> **Superseded 2026-10-23 by [ADR-019](ADR-019-lean-delivery.md):** issues close at merge (`Fixes #N`); `wiki.yml` only publishes `docs/wiki/`. Kept as history.

Status: engineering decision for the delivery process, pending maintainer review.
Date: 2026-10-14. Change record: CHG-DEV-WIKI-001 (`../change-records-archive.md`). Issue: #5.
Affected IDs: R40 (document-to-code traceability). No requirement, screen, route, operation, schema or
application code changes. Amends ADR-010 #1 (closing keyword).

| # | Topic | Decision | Reason / open dependency |
|---|---|---|---|
| 1 | Authority | `spec/` stays authoritative for product and engineering requirements. The Wiki summarizes it for readers and links to it. `docs/wiki/` on `main` is the reviewed source of the managed Wiki pages listed in `docs/wiki-publication.json`. | One reviewed source; the Wiki is an output. |
| 2 | Wiki repository | Publication goes to `<repo>.wiki.git`. The script discovers the Wiki's default branch with `git ls-remote --symref` and never assumes it. Unmanaged Wiki pages are never written or deleted. Managed pages are never deleted. | Preserve other people's pages. |
| 3 | Import before managing | `issue_completion.py import` fetches an existing Wiki, copies colliding managed pages out for review, and reports unmanaged pages. Its result (Wiki commit, adopted page hashes) goes into `docs/wiki-publication.json` through a PR. Publication replaces a managed page only if the remote copy is absent, already equal, adopted at import, or exactly what this workflow last published. Any other remote edit stops publication until it is reconciled into `docs/wiki/`. | No silent overwrite of Wiki-editor changes. On 2026-10-14 the Wiki repository did not exist, so nothing was imported. |
| 4 | Issue references | PRs and commits use `Refs #N`. `Closes`, `Fixes` and `Resolves` are not used for issues, so a merge never closes an issue. | Closing keywords close on merge regardless of documentation. |
| 5 | Explicit readiness | The label `ready-for-completion` is the explicit record that a maintainer judged the acceptance criteria met. A reference, a merge or a Project status alone never authorizes closure. | Track readiness explicitly. |
| 6 | Readiness checks | Before anything is published for an issue: open; labeled; a valid Issue Work Log entry for it on the default branch; no unchecked `- [ ]` criteria in the issue body (resolution Completed); every listed PR merged into the default branch with its merge commit contained in the published source, and accepted: an approving review, no review requirement, or **maintainer acceptance** (no approving review, but the PR was merged by a repository admin or maintainer **and** the readiness label was applied by an admin or maintainer; amended 2026-10-14 by the maintainer's choice, CHG-DEV-WIKI-002). A "changes requested" review always blocks; and no open PR referencing the issue. Duplicate and not-planned issues need a decision entry instead of PRs. | Multi-PR issues stay open until all criteria and PRs are done. Maintainer acceptance exists because the sole maintainer authors and merges PRs through the organization ruleset's bypass, and GitHub never lets an author approve their own PR. The completion comment states which acceptance applied to each PR. |
| 7 | Completion sequence | Readiness → publish from the default-branch tip (no force push; a rejected push refetches and retries three times) → fetch the Wiki again and compare every managed page byte-for-byte, plus the issue's work-log entry → evidence (source commit, Wiki commit, page hashes) → completion comment with a hidden marker → close with `COMPLETED`, `NOT_PLANNED` or `DUPLICATE` → the project board Status `Done`. A failure before closing leaves the issue open. A Project failure after closing exits 4 and is retried by `sync-project` and the hourly sweep. Neither retry duplicates the comment, the Wiki commit or the closure. | Requested order; idempotent steps. |
| 8 | Provenance | Each publication commit carries `Source-Repository:` and `Source-Commit:` trailers. They are generated at publication, after merge; no file contains its own future commit SHA. The completion comment records the source commit and the Wiki commit. | Requested provenance rule. |
| 9 | Monotonic publication | A source that is an ancestor of the last published source is never published (`newer-exists`). A source that diverged from it fails. An identical tree produces no commit. | Never overwrite newer documentation with an older snapshot. |
| 10 | Trust and credentials | `wiki-completion.yml` runs only on push to `main`, issue events, a schedule and manual dispatch, never on `pull_request`. It checks out the default branch and uses `persist-credentials: false`. The Wiki push uses `WIKI_PUSH_TOKEN` (or the job token, explicitly tested by the push result) through a transient git credential helper that reads the environment, so tokens never appear in URLs, files or arguments. Project writes need `PROJECT_TOKEN`; `GITHUB_TOKEN` cannot write organization Projects. | PR code never sees publishing credentials. |
| 11 | Premature-closure guard | On `issues: closed`, an issue without the completion marker that was closed by a commit or PR keyword, a bot or an app is reopened with one comment per close event. A person's manual closure is reported in the run log and not reverted. | Closure through the GitHub UI by someone with triage rights is not prevented, and this record does not claim otherwise. |
| 12 | Repository auto-close setting | Neither the REST repository object nor GraphQL `UpdateRepositoryInput` exposes an "auto-close issues with merged linked pull requests" setting (checked 2026-10-14), so it could not be changed or verified through the API. #4, #10 and #11 are the controls instead. | Infrastructure lead: check the repository settings page and turn the setting off if it exists. |
| 13 | Project automation | the project board has built-in workflows enabled: "Item closed", "Pull request merged", "Auto-close issue" and others. "Pull request merged" can set Status Done, and "Auto-close issue" then closes the issue. The API can only delete these workflows, not disable them; deleting a shared Project's automation is not reversible here, so it was not done. The guard reopens such closures. | Done 2026-10-14: the project owner disabled "Auto-close issue" and "Pull request merged" (verified through the API). The guard stays as a backstop. |
| 14 | Claude sessions | `.claude/rules/github-work-tracking.md` makes the rule unconditional for Claude: complete issues only through `scripts/issue_completion.py`, never with `gh issue close`. | Persist the behavior across sessions. |
