| # | Topic | Decision | Reason / open dependency |
|---|---|---|---|
| 1 | Work tracking | One issue per change, an issue-linked branch `chore/<issue>-<topic>`, a draft PR that says `Refs #<issue>` (amended by ADR-011 #4: closing keywords are not used), and `.github/pull_request_template.md`. | No repository or organization "work-tracking rule" file was found. This follows `<owner>/.github` CONTRIBUTING (branch prefixes, PR template, `ci:` commit type) and `product.md` "Required workflow for every change". Adding the issue to the configured GitHub Project needs a token with the `project` scope. Issues close only through the Wiki completion workflow (ADR-011). |
| 2 | Actions | Only actions on the repository allowlist, pinned to full commit SHAs that HP's reusable workflows already use (`checkout` v6.0.2, `setup-node` v5.0.0, `upload-artifact` v6.0.0, `download-artifact` v8.0.1) plus `setup-python` v6.3.0. Docker, `gh` and `uv` are called as CLI tools. | The allowlist does not include `astral-sh/setup-uv`, `docker/setup-buildx-action` or `docker/build-push-action`. |
| 3 | Permissions | Every workflow sets `permissions: {}`, and each job asks only for what it uses. `packages: write` exists only in the release build job and `contents: write` only in the release draft job. The deploy job has `contents: read` + `packages: read`. Registry logins use a job-scoped `DOCKER_CONFIG` that is deleted after the job. | The repository default token permission is `write`; explicit job permissions override it. |
| 4 | Runners | CI: `vars.AWARE_CARE_CI_RUNNER` or GitHub-hosted `ubuntu-latest`. Release build: `vars.AWARE_CARE_ARM64_RUNNER` or GitHub-hosted `ubuntu-24.04-arm`. Deployment: a self-hosted runner on the Nano, labels from `vars.AWARE_CARE_NANO_RUNNER_LABELS` (default `["self-hosted","linux","ARM64","aware-care-nano"]`). | HP's reusable workflows use `hpip-devex-codeway-al2023`, but its runner group and architecture could not be confirmed for this repository (organization runner listing needs `admin:org`). No runner is registered for this repository. The defaults are placeholders until the infrastructure lead confirms them. |
| 5 | Package format | Two OCI images per release, `aware-care-api` and `aware-care-web`, built for `linux/arm64` and pushed to `ghcr.io/your-github-user/aware-care/`. Deployments pull by digest only. Base images (`python:3.12.15-slim-bookworm`, `ghcr.io/astral-sh/uv:0.13.0`, `node:24.21.0-bookworm-slim`, `nginxinc/nginx-unprivileged:1.29-alpine`) are pinned by multi-arch digest. | Docker 29.2.1 (arm64) is already installed on the Nano. The toolchain versions match the observed development tools. HP-approved base-image sources were not found; replace them if HP mandates an internal registry. |
| 6 | Verified commit | `release.yml` runs only from `main`. It requires the commit to be on `main`, a successful `ci.yml` push run for that exact SHA, and a new `v<semver>` tag. It re-runs traceability, contracts and backend acceptance (mock) on the arm64 runner, builds from that SHA, then creates an annotated tag whose message carries the release manifest, and a **draft prerelease**. Publishing the release is manual (amended 2026-10-26, #600: `scripts/release/release.sh` publishes it, still a prerelease, after every selected device deployed and passed its smoke; ADR-019 #5). | "Exact verified commit". The tag message is readable with `contents: read`, so deployment does not need write access to see a draft release. |
| 7 | Container-to-host loopback | Both containers use **host networking** and bind `127.0.0.1` only: API on 8100, web gateway on 8180. Container loopback is therefore the host loopback, where ZRT listens (`127.0.0.1:8080`). No port is published and no service is re-bound to a bridge interface. | `host.docker.internal`/`host-gateway` would require ZRT to listen on the Docker bridge, which changes ZRT configuration and widens its exposure. The app's loopback-only `AWARECARE_MODEL_BASE_URL` validation stays unchanged. |
| 8 | Ports | The demo deployment uses 8100 (API) and 8180 (web). The browser reaches it through `ssh -L 127.0.0.1:18180:127.0.0.1:8180`; the API allows exactly `http://127.0.0.1:18180`. | 8000 and 5173 stay with the development servers (ADR-001, CLAUDE.md), which run on the same device. 8080, 10050, 11000, 11434, the SSH port and the test ports 15174/18000 are taken. Conflict noted: CLAUDE.md names 8000 as "the application API"; this record keeps that for development and gives the deployed stack its own ports. |
| 9 | Web serving | The web image serves the Vite production build from unprivileged nginx and proxies `/api` unchanged to the API. Access logs are off. Every route falls back to `index.html`. | The Vite dev server is not a deployment gateway (deployment.yaml). This is still not the future trusted-network TLS gateway (ADR-005). |
| 10 | Explicit mode | `deploy-nano.yml` requires `mode` = `mock` or `local` with no default. Local mode needs a model ID (input or environment variable `AWARE_CARE_MODEL_ID`) and first reads `GET http://127.0.0.1:8080/v1/models`. If the ID is not served, the deployment fails before any container changes. After start, local readiness and the flow check must pass with non-mock guidance. Otherwise the run fails and the previous deployment is restored. There is no fallback to mock. | CLAUDE.md, R26, R34. The current build reports local readiness `unavailable` (no reviewed pathway), so every local deployment fails until ADR-002 to ADR-004 are resolved. That is intended. |
| 11 | ZRT and GPU separation | The deployment never runs `zrt` commands, never passes `--gpus` or devices, and never changes ZRT, drivers or CUDA. The ZRT check is a read-only HTTP GET in local mode only. | ENG-07 and CLAUDE.md. |
| 12 | Runtime data and credentials | Data, state, evidence and an optional `secrets/api.env` (mode 0600, server-only) live under `vars.AWARE_CARE_DATA_ROOT` or `~/.local/share/aware-care-demo`, outside Git and the images. Mock and local data directories are separate. `.dockerignore` is an allowlist. The images contain code, locked dependencies, the synthetic fixture pack and the two observational infra records. | CLAUDE.md "Keep credentials, runtime databases, uploads and health payloads outside Git". The app currently reads no credential; `api.env` is only the injection point. |
| 13 | Serialization and rollback | Workflow `concurrency: deploy-demo-zgx-nano` (no cancellation) plus an `flock` on the device. The running containers are parked as `*-previous` until the new release passes readiness and the flow check. On failure they are restored and re-checked (`ROLLED_BACK`), and the run still fails. Manual rollback: dispatch `deploy-nano.yml` at the previous tag, or run `nano_deploy.py rollback` on the device. | One device and fixed ports leave no room for blue/green. Parked containers make rollback independent of the registry. |
| 14 | Evidence | Each deployment writes `deployment-evidence.json`: release, commit, mode, image digests, preflight, ZRT check, readiness, flow-check step statuses and timings, and the rollback outcome. It goes to a workflow artifact (90 days) and to `<data_root>/evidence/`. It contains no request or response bodies. | R37, R38 and `evidence/README.md`. This is deployment evidence, not requirement verification; it does not move any status to `verified`. |
| 15 | NOT_EXECUTED reporting | The CI gate and release notes report executed test counts separately from the `spec/acceptance.json` statuses. A missing report is `NOT_RUN`. Registry `NOT_EXECUTED` is never counted as passed. | verification.md and authority.md "Truthful status". |
| 16 | Registry reachability on the Nano | The Docker daemon on the Nano has no proxy configured and cannot reach `ghcr.io` or Docker Hub; the shell reaches them through the site proxy. Deployments pull images through the daemon, so they fail until the daemon is given the site proxy (or a mirror). This record does not change the daemon. | Observed 2026-10-14 (`docker pull ghcr.io/...`: context deadline exceeded). Infrastructure-lead action; see the runbook's setup steps. |
