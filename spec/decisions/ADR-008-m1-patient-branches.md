# ADR-008: Milestone 1 patient-reachable urgent and limited branches (mock mode)

Status: engineering decisions for the development build, pending product/clinical review.
Date: 2026-10-13. Change record: CHG-DEV-APP-002 (`../change-records-archive.md`). Extends ADR-007; does not replace it.
Affected IDs: R11, R14, R15, R17, R35, R37; A01, A05, A07, A12, A15; M04, M05, M08, M11;
saveAnswer, generateGuidance, getGuidance, createSession, getReadiness, deleteSession.

No requirement, route, operation ID or schema changes. Each item should be confirmed or replaced by the named owner.

| # | Topic | Decision in this build | Reason / open dependency |
|---|---|---|---|
| 1 | Urgent-at-answer trigger | In mock mode, A05 shows **Simulate urgent answer** (the fixture `urgent.alternate_trigger`). It sends `saveAnswer` with `status=answered` and the reserved structured value `["fixture:urgent-signal"]`. `modules/safety/service.py` recognizes it only when mode is `mock` and the case is in `intake`. The case moves `intake → urgent` with a new revision. The issued prompt becomes `invalidated` and keeps its slot (R11). A synthetic fact `fixture:urgent_signal` is recorded and no answer value is stored. `next_action=urgent`. | ADR-007 #2 blocks presenter `loadScenario`, so without this the urgent branch is unreachable from the patient UI. The value is a list that no question type accepts as an answer and is never free text (`free_text_controls_outcome: false`). In local mode, or outside intake, it is rejected as `ANSWER_INVALID` (422). Clinical owner: ADR-003. |
| 2 | Urgent at concern/edit/record | Not added. Concern-level urgent remains reachable only via presenter `loadScenario` (blocked, ADR-005). Records are unavailable (ADR-007 #4). | `CaseWrite`/`CaseEdit` carry no fixture selector, and free text must not select outcomes. |
| 3 | Limited-information outcome | After strict validation, the guidance service applies `safety.apply_information_limits`. Any unanswered issued slot adds reason code `LIMITED_INFORMATION` and a leading uncertainty. Gaps turn a `self_care_candidate` into `routine_clinician`/`discuss_with_clinician`. With no answers at all, the level is `undetermined` ("Limited information"). It never lowers urgency. A07 shows a "Limited information" banner. | R14: “a remaining critical gap prevents reassuring self-care guidance”. The fixture pack defines no reviewed required/critical fields, so every gap is treated conservatively as critical. Clinical owner: ADR-003. |
| 4 | Reset and another case | A07, A12 and A15 offer **Start another case** (`/app/new`, same session) and **End session and reset**. The reset calls `deleteSession`: the session is revoked, the guest's cases are purged, in-memory state is cleared, and the user goes to A01 with a confirmation. | Patient-side reset uses existing operations only. Presenter `resetDemo` stays presenter-only (ADR-005). |
| 5 | Pre-session nonce on direct load | When `createSession` returns `PRESESSION_REQUIRED`, A01 calls `getReadiness` (which issues the nonce cookie) and retries once with the same idempotency key. | A direct load or refresh of `/app/start` makes no earlier `/api` call. Before this fix the guest was stuck: the "Reload" advice could never succeed. |
| 6 | Browser test stack | `apps/web/playwright.config.ts` starts an isolated API (127.0.0.1:18000, mock mode, temporary data dir, origin allowlist `http://127.0.0.1:15174`) and Vite (127.0.0.1:15174). Vite gains env-only overrides `AWARECARE_WEB_PORT` and `AWARECARE_API_TARGET` (loopback only); defaults stay 5173 → 8000. | Keeps the running dev servers, their data and the ADR-007 #13 origin untouched. |
| 7 | Intake → review transition | After the last answer (`next_action=review`), A05 calls `nextQuestion` before routing. The server moves `intake → review` only when it reports `review_required`. | Defect found by browser tests: A05 used to navigate straight to A06 while the case was still `intake`, so the review could not be confirmed. |
| 8 | CSRF token after reload | On `403 CSRF_REJECTED` for a write, the client makes one authenticated GET (`getSettings`, which echoes the token per ADR-007 #7) and retries once with the same body and idempotency key. | Defect found by browser tests: a direct load or refresh of a write screen (e.g. A03) lost the in-memory token. The server rejects before any effect, so a single retry is safe. |
